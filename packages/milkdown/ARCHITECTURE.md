# Architecture

`@cherry-markdown/milkdown` is a standalone WYSIWYG editor, not a Cherry editor-mode plugin.

- `editor.ts` owns the Milkdown lifecycle and public instance API.
- `recovery-context.ts` owns the lifetime of cached or lazily recovered error snapshots; the editor decides when a snapshot is needed and how it is serialized.
- After teardown completes, the per-editor plugin configuration releases its engine and application callbacks so shared Milkdown plugin definitions do not retain them. Pending renderer cleanup keeps only the error reporter needed to report a late cleanup failure; application-owned references and unresolved renderer work can still extend resource lifetimes.
- `CherryEngine.makeHtml(markdown)` renders Cherry-owned native syntax; registered visual renderers handle Mermaid, ECharts, and custom fenced blocks.
- Engine HTML cannot install document-wide stylesheets, including styles embedded in SVG. Explicitly registered visual renderers can mount DOM directly and retain SVG styles in string results for diagram compatibility, so applications must treat those renderers as trusted code.
- Cherry dist imports are isolated behind `cherry-engine.ts`, `cherry-echarts.ts`, and `cherry-codeblock-echarts.ts`; these are the package-upgrade checkpoints. The published Cherry stylesheet remains an explicit CSS dependency.
- Table and fenced charts share one Milkdown-owned mount/cleanup path. It uses Cherry's existing option generator and chart lifecycle, including the minimum declared in `peerDependencies`, without adding a Cherry mounting API or depending on Previewer DOM. Charts in one editor share a reference-counted engine, matching Cherry's root-scoped export/theme observers; each mount owns its request-cancellation scope. Cleanup and resize resolve the current chart after export rebuilds, and the final mount releases the engine. Consumer checks apply Changesets in a disposable workspace and exercise the versioned tarballs, including registered maps. They also test the published minimum when available; before its first publication, the planned core tarball must match that minimum exactly.
- `cherry-map.ts` owns map fetching, cancellation, fallback and retry for Milkdown mounts. Export rebuilds reuse the pending request; completed maps still use Cherry's existing option generator for province normalization, chart data and themes. The per-instance adapter routes only owned map mounts, never replaces browser globals, and requires no cancellation API in Cherry. Cherry's only integration fix is selecting the injected ECharts registry consistently instead of an unrelated global instance.
- `scripts/sync-cherry-helpers.mjs` bundles Cherry's pure clipboard, image-layout and link-scheme helpers into `src/generated/`. Inline grammar and image directive patterns are generated from Cherry's actual rule builders and helper methods. `--check` detects drift, and production builds include the generated runtime without importing Cherry source or UI at runtime. Handwritten declarations describe this private integration boundary. Milkdown's interactive copy controls use `copy.ts` to coordinate cancellation and fallback across editors without changing Cherry's clipboard API.
- `inline-syntax.ts` is the single adapter between those generated rules and both Markdown import and live input. Input-only delimiter precedence avoids consuming unfinished background-color/subscript syntax; capture indices retain payloads equal to their attributes. Original AST source ranges protect escaped delimiters after Markdown decoding.
- Its legacy locale context is generated from Cherry's chart messages during build (`sync-chart-locale.mjs`), not an independently maintained translation table. It does not import Cherry's editor/toolbar runtime to obtain translations.
- Markdown source reconciliation accepts a formatting-preserving edit only after parser/serializer validation. Ambiguous matches fall back to canonical serialization rather than changing the wrong occurrence. Nested renderer results share an abort-owned cleanup scope, including late results after sibling failures.
- `markdown-reconcile.ts` proposes bounded source edits and owns the canonical fallback; `markdown-source-map.ts` can locate a literal text edit when the raw and serialized Markdown trees match apart from source positions. The editor supplies the active remark parser and validates every proposed result against the live document. This is a per-reconciliation check, not a persistent ProseMirror transaction-to-source map: escapes, transformed or structurally different trees, and failed validation can fall back to canonical output. Parsing and validation can add noticeable synchronous work in large documents.
- Source reconciliation preserves a uniform CRLF convention when converting the serializer's output passes parser validation. ProseMirror owns undo and redo. A bounded cache associates recent serialized states with an unambiguous source line-ending convention and suffix; history transactions can restore these after parser validation. Mixed endings and conflicting conventions are never guessed, and external content changes clear the cache. Evicted or ambiguous states retain the normal reconciliation result.
- Markdown's parsed code/HTML nodes own literal source boundaries, including nested indented code and incomplete fences. Cherry directive and reference scans share those protected ranges; visual fenced nodes take their language and payload from the same AST instead of parsing fences a second time. Complete blocks between directives reuse their original AST and document-wide reference context; only partially split blocks require reparsing.
- `table-focus.ts` isolates Table Block's pointer/word selection integration. Table editing and controls remain Milkdown-owned; selection updates use ProseMirror transactions, never replacement of component DOM.
- `composition-gate.ts` only schedules/coalesces external writes until native composition commits. `document-update.ts` shares structure-checked ProseMirror transforms with ordinary updates and rebases the latest deferred update over native input. A known empty editor-only tail is omitted from source comparison without changing the view; real or ambiguous trailing content remains intact. Overlapping/ambiguous ranges preserve local input and report a conflict; same-value echoes do not cancel a distinct update. This bounded IME reconciliation is not a collaborative merge protocol. ProseMirror remains the caret/history owner, and concurrent local input still emits its merged value even for a silent external write.
- ECharts shares Cherry's CSS-derived theme and observer for table and fenced charts. Instance-local theme notifications redraw only Mermaid's preview, leaving source DOM and ProseMirror selection untouched. Renderer cleanup/error reporting share one exception-isolated lifecycle scope.
- `wysiwyg/` owns ProseMirror schema extensions, NodeViews, source editing, and editor-local overlays.
- `compound-selection.ts` synchronizes only native mouse text ranges inside editable compound content before ProseMirror's delayed pointer synchronization; rendered atoms and external controls keep their own selection behavior.
- `pointer-caret.ts` maps a stationary mouse click back to a text position when a blurred editor regains focus, so delayed view synchronization cannot restore an older caret. Drags, controls, and positions outside the clicked text block are left to the browser and ProseMirror.
- Image controls inspect animations once per frame only while an image is selected, allowing CSS and Web Animations started later to be detected; observation stops on dismissal or destruction. Confirmed opacity-only animations do not move the anchor. Paused geometric effects get a position check so timeline seeks move the controls; changing their paused animation state during a resize cancels that resize. Controls follow known continuous movement and hide resize handles during it. Finite or unrecognized animations wait for finish/cancel events; pending listeners are removed on focus loss, pointer interaction, leaving image selection, or editor destruction. An unrecognized continuous effect can still keep controls hidden.
- The text-formatting Bubble stays hidden while a primary pointer gesture is active and updates after release or cancellation, so it cannot cover the selection path. Document-level listeners are released on editor destruction.
- `clipboard-boundaries.ts` preserves missing edge spaces only when a single-line HTML paste exactly matches its plain-text counterpart otherwise; Milkdown handles all other clipboard parsing and rich blocks.
- The packed-consumer check exercises real Chromium clipboard paste, undo and Markdown reload, CRLF editing, compound-block mouse selection, refocusing from a host input, and native composition with an external update against the installed package.
- `wysiwyg/nodes.ts` only assembles the existing registration order and exports. Its `nodes/` modules separate schemas, compound containers, footnotes, source/navigation nodes, and rendered embeds; feature modules never import the assembly entrypoint.
- Relocated footnotes leave a dedicated editable layout gap. Empty gaps are omitted from Markdown, while typing converts the gap to a normal paragraph; splitting can still create a real empty paragraph. Segment parsing discards gaps introduced only by supplemental definitions.
- Footnote numbering is a derived decoration of the current document order. Reference and definition views consume it without changing Markdown or adding history steps; an unreferenced definition remains editable and has no misleading navigation target.
- The footnote gap marker is not accepted from imported HTML. Copying removes empty internal gaps from the clipboard slice while preserving user-authored empty paragraphs and valid parent structure.
- Undo can restore a uniquely remembered source spelling beyond list markers only after parsing it and comparing the complete document structure, marks and attributes with the live editor. An auto-generated heading ID and the known editable tail are handled separately; ambiguous or mismatched states keep the current serialization.
- Teardown drops the editor's internal references to consumer options, engines and its public instance after cleanup. A caller that retains the public instance still retains its `engine`; pending renderer cleanup keeps the callback it needs. Dependency-owned history caches may still retain the removed view temporarily.
- Renderer cleanup scopes retain their error reporter for late results; the destroyed lifecycle releases its own reference. The reporter is created outside NodeView constructor closures so a cached view does not retain it after the scope finishes.
- `render-lifecycle.ts` shares pending/committed render ownership for embeds and table-chart previews. It commits only the current revision, retains the old preview until success, and releases cancelled/late results through the existing renderer cleanup scope. NodeViews still own DOM, source editing, and error presentation.
- `contextual-ui.ts` shares contextual control geometry, selection-preserving pointer behavior, viewport subscriptions, and frame scheduling. Text, link, and image plugins keep their own visibility/actions and existing placement policies; no shared global overlay state or Cherry DOM rewriting is introduced.
- `renderers/` contains optional heavyweight renderers such as ECharts.
- `styles.css` imports Cherry's published stylesheet and adds only scoped editing-state CSS.

The package must not instantiate `Cherry`, Previewer, CodeMirror, or Cherry toolbar/Bubble classes. Reusing a Cherry CSS class is a visual contract only and must not imply runtime coupling.

Cherry's published standalone Engine entry has no matching subpath type declaration. The public `engine` input therefore accepts an object and validates `makeHtml()` when creating the editor; the packed-consumer test covers this boundary.

ECharts fenced blocks use Cherry's code-block addon's `parseOption()` and its default data-only policy. Milkdown mounts the chart itself because Cherry's `render()` locates a Previewer DOM node. Mermaid's Cherry addon has the same Previewer dependency, so the Milkdown-owned renderer and source control need explicit browser regression coverage when Cherry or Mermaid changes. These editor controls are ProseMirror NodeViews, not Cherry editor controls.

Ordinary editable code blocks use Prism decorations rather than Cherry's static code-block DOM. `scripts/sync-cherry-prism.mjs` builds their runtime from Cherry's bundler-independent `build/prism.js` transforms, which own the `build/prism-languages.json` list, Babel dependency/alias loader and scoped Prism core compatibility rewrite. Cherry's Vite adapter and Milkdown's esbuild generator call these same transforms; Milkdown does not invoke Vite plugin hooks. The generated JavaScript is ignored by Git, regenerated before package builds, unit tests and demo development, and copied into the published dist with its license; consumers need no Cherry build files or custom bundler plugin. Milkdown runs Prism's public before/after token hooks before creating decorations, so template and embedded-language extensions follow Cherry as well. Unknown languages retain Cherry's JavaScript fallback. The controls and editable DOM remain Milkdown-owned. The token-style contract test compares both renderers by character, including aliases and dependent extensions; headless ESM and packed-consumer checks cover the generated runtime. Mermaid rendering uses one temporary canvas per revision and serializes calls, matching Cherry's shared-renderer concurrency boundary.

Markdown is the source of truth. Standard syntax uses Milkdown nodes and marks. Cherry-specific syntax is structurally editable only when parsing and serialization are deterministic; otherwise recognized source blocks are retained as atomic raw nodes rendered through CherryEngine. There is no blanket byte-preservation guarantee for unknown syntax that is not recognized by the adapter. Renderer failure is isolated to the affected node.

NodeViews may mount optional renderers only into elements they create and own. They must not discover, rewrite, or append controls to class names inside HTML returned by `CherryEngine.makeHtml()`. Renderer callbacks are trusted application code; returned HTML strings pass through the package sanitizer before mounting. Compound Cherry blocks therefore expose one block-level source editor unless Cherry publishes a stable child-rendering contract in the future.

Every editor owns its overlays, observers, timers, NodeViews, and renderer instances. `destroy()` removes only the child mount created by this package and never removes consumer-owned root content.

## Reuse boundaries

| Surface           | Shared Cherry logic                                                 | Milkdown-owned interaction                                        |
| ----------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Links             | Scheme validation                                                   | Selection ranges, clipboard, form and ProseMirror transaction     |
| Images            | Image rendering, layout grammar and decoration/alignment state      | Attribute form, resize, upload ownership and document updates     |
| Code blocks       | Prism appearance checked against Cherry                             | Editable NodeView, clipboard, language control and selection      |
| Table charts      | Engine table recognition, options, data, chart generation and theme | GFM table edits, scheduling and stable chart mounts               |
| Inline extensions | Cherry-generated syntax rules shared by import and live input       | Schema, serialization, delimiter precedence while typing and undo |

Generated modules are build artifacts with Cherry as their source of truth. Do not hand-edit them or import Cherry toolbar/Previewer controllers to reuse a pure operation. Existing controls retain their DOM, class names and styles; visual parity checks supplement behavior tests.

## Table-chart parsing

`wysiwyg/table-chart.ts` delegates table recognition, options and cell data to the published Cherry Engine. A short-lived Engine is configured with the existing `chartRenderEngine` extension; its `render(type, options, table)` callback captures a descriptor directly. No Cherry source import, private method, generated table parser, presentation-DOM query, or ECharts instance is needed for parsing. The dedicated parser uses Cherry's default table rules with charts enabled; it does not inspect injected-engine internals or inherit application callbacks. Business-specific dialects remain the responsibility of custom renderers. Native layout charts keep the existing package-owned descriptor marker; both paths decode the Engine's HTML transport layer once.

Milkdown's immutable table node remains the editable source of truth. The adapter only serializes cell text into Markdown; Cherry owns splitting, column padding and chart-option semantics. Header-only recognition has a separate bounded cache, unchanged table nodes reuse revisions via a WeakMap, and complete table parsing stays behind the existing redraw debounce. Each parser cache holds at most 32 entries and skips sources/results longer than 32,768 UTF-16 code units; callers receive fresh objects. A fresh Engine on a cache miss prevents its internal HTML caches from retaining an unbounded series of edited table snapshots.

Chart widgets retain their identity across mapped document positions, so changing an earlier table does not recreate unrelated charts. ProseMirror supplies each retained widget's current position. Milkdown continues to own cell selection, history and IME; its native table component may rebuild selection chrome independently of chart rendering. Neither CSS nor the control DOM structure changes.

Compatibility follows Cherry, rather than JSON5: standard JSON options use double-quoted keys and no trailing commas; Cherry's deprecated legacy key/value options remain accepted. Invalid standard JSON follows Cherry's fallback and diagnostics. Bare pipes inside backticks receive Cherry's table behavior; escape cell pipes as `\|`. Ragged rows, compact delimiters and escaped cells also follow Cherry. ECharts _fenced-code_ options still use Cherry's data-only JSON5 parser. Parsing is not guaranteed to cost less than the former handwritten splitter: the performance contract is no full-table parse on each body keystroke, bounded caches, coalesced redraw, and no unrelated chart remounts.

`test/table-chart-parser.spec.ts` compares the adapter with native Engine output and exercises compatibility, unsafe keys, non-execution and cache bounds. `test/table-chart-updates.spec.ts` verifies that 50 synchronous edits across a five-table/500-row document trigger one deferred full parse. `e2e/table-chart-parser.spec.ts` exercises real editing, undo, URL queries and stable chart mounts, and records whole-operation timings as diagnostic artifacts rather than enforcing hardware-dependent millisecond thresholds.

## Test and CI entry points

Tests use the repository's Vite+ commands and configuration entry point. Run these commands from the workspace root:

- `vp run test`: Cherry, MiniProgram and Milkdown unit tests, including the existing security regressions.
- Milkdown unit tests prepare only Cherry's public Engine Core ESM and the table/code-block ECharts addon ESM entries through the new opt-in `vp run -F @cherry-markdown/milkdown build:cherry-runtime` entry. This preparation profile belongs to Milkdown and calls Cherry's shared builders with explicit target/format arguments; it does not add or change Cherry package scripts. Tests still exercise built Cherry runtime files rather than aliasing those imports to source. Existing Cherry `build:engine`, `build:core`, `build:stream` and `build:full` commands retain their historical complete ten-file JS output; their names do not narrow that compatibility contract. The default Cherry `build` retains the complete release output matrix, including addons, styles, fonts and declarations.
- `vp run -F @cherry-markdown/milkdown test:coverage`: Milkdown unit tests with coverage thresholds enabled.
- `vp run test:e2e:milkdown`: the complete Chromium interaction suite.
- `vp run -F @cherry-markdown/milkdown test:e2e:matrix`: shared behavior, editing boundaries and table-chart parser regressions on Firefox, WebKit and touch Chromium. The file selection lives in `playwright.config.ts`, not workflow YAML.
- `vp run -F @cherry-markdown/milkdown test:consumer`: build and validate planned-version package consumers. `test:consumer:prepared` packages existing builds without rebuilding them. The current PR workflow does not run `test:consumer:ci`; consumer validation must be run separately.
- `vp run -F @cherry-markdown/milkdown test:artifacts`: published-file and artifact provenance contract tests. Consumer validation checks the packed exports, styles, declarations, generated runtime files, licenses and relative runtime imports.

The browser commands build Cherry by default. The current PR workflow builds Cherry, Milkdown and the demo in one job, then runs Chromium with two workers and `MILKDOWN_E2E_DEMO_PREBUILT=1`. It does not run the browser matrix or packed-consumer validation. The separate artifact preparation scripts record the checkout commit, uncommitted working-tree changes, exact Node.js version and SHA-256 digest of every file; receivers reject mismatched or modified artifacts. This detects source changes after packaging, but does not prove that an existing build was current when packaged: build the packages before preparing artifacts.

The separate consumer checks use normal npm peer resolution with `--strict-peer-deps`, never `--legacy-peer-deps`. Their planned-version and release tarball variants exercise a base build and browser editing with MathLive absent, minimum Cherry compatibility, ECharts/table charts/maps/Prism/theme switching, and Mermaid plus MathLive formula rendering and source editing with the optional peers installed. Runtime failures retain screenshots and error diagnostics. The compressed-size workflow includes Milkdown's dist JavaScript/declarations and its published root stylesheet; this is a per-file gzip comparison, not a browser bundle budget.

Consumer checks compare every installed Milkdown file with the verified tarball before each build and browser run. Preparing or consuming the Cherry tarball also requires its declared runtime, stylesheet and type entries, Engine Core and both ECharts addons; a source checkout without built Cherry artifacts is rejected. The base browser scenario also verifies that a custom Engine cannot install a document-wide SVG stylesheet.

Cherry and Milkdown generate text, JSON and HTML unit coverage reports by default. The unit-test CI job uploads both packages' reports, including available reports after a test failure. As with Cherry, thresholds are opt-in through `COVERAGE_THRESHOLDS` and the package's `test:coverage` command; the ordinary root test command does not enable this gate. MiniProgram keeps its existing test configuration.

The current local unit-test measurement is 75.92% statements, 59.10% branches, 81.28% functions and 79.61% lines. The existing opt-in thresholds are 77%, 59%, 82% and 81%, respectively, across `src/**/*.ts`, excluding declaration files in addition to Vitest's default exclusions; statements, functions and lines remain below those thresholds. These measurements do not include browser or consumer-test coverage. Keep those separate regressions even when the unit threshold passes; improve meaningful unit coverage rather than lowering the thresholds solely to make the gate pass. Cherry's existing thresholds are unchanged.

Despite its historical name, `milkdown-browser-consumer` currently aggregates only the unit-test and Chromium jobs. It does not prove consumer installation, cross-browser behavior or the optional coverage threshold. Typechecks and Node build compatibility remain in the separate CI-check workflow.

The complete-manual round-trip fixture has a dedicated 30-second timeout for coverage on shared CI runners. The five-table/500-row coalescing test and the React StrictMode initialization race use 20-second limits for concurrent test workers; their functional assertions remain unchanged. Other unit tests retain the default timeout; no fixture or assertion is skipped. Declaration files are excluded from executable coverage to avoid uncovered-file parsing errors.

Preview workflows build only their required packages: the playground builds Cherry, pkg-pr-new builds Cherry, MiniProgram and Milkdown, and the Tauri workflow builds Cherry before Tauri invokes the client frontend build. Full workspace builds and published-artifact checks remain in the Node compatibility matrix. Consumer and optional coverage checks must be run separately from the PR browser job.
